# Build Phases

Execution order for the FYP build. Each phase should be demo-able before moving to the next.

**Renamed TAMEER → Buniyad (2026-09-25).** A live Pakistani company, Tameer.ai, already operates under the near-identical name in this exact space (construction marketplace + cost calculators, apps on both stores) — found via competitor research, not something we could safely ignore or discover later at defense. Every reference across the codebase, docs, and the local Postgres database (`tameer` → `buniyad`) has been renamed and re-verified end-to-end (19/19 checks, zero errors). "Buniyad" (بنیاد, "foundation") was screened for collisions before adopting it; no formal trademark check has been done.

**Pricing recalibration (2026-09-25).** Material rates in `data.py` are now sourced from current Pakistani rate-guide research (cement, steel, bricks, sand, aggregate, paint, tiles) rather than invented numbers — dated, documented in the module docstring, still not the same as a licensed source. This surfaced a real accuracy problem: the flat per-sqft benchmarks for electrical/plumbing, woodwork and finishing were landing at roughly a third of what published Pakistani cost guides report for those categories, so a "fully finished" house was under-priced relative to its own grey-structure cost. Recalibrated against two independent research anchors (per-category PKR/sqft ranges, and a separate 10-Marla grey-vs-finished total comparison) — the same 10 Marla/Rawalpindi/2-storey/standard scenario used throughout this project moved from 88.2L–103.6L to 107.0L–125.6L, now landing inside the ~9–12M PKR published range for a finished 10-Marla house instead of below it. Quantity-per-sqft ratios and bylaw coverage ratios are still unverified — this pass fixed the price side of "quantity × price," not the quantity side.

**UI trust/elevation pass (2026-09-25).** Response to "doesn't feel premium/trustworthy enough": every `Card` in the app had zero shadow (a 1px ring only) — replaced with a proper theme-aware layered shadow, the single highest-leverage change since it's one shared component. Added `tabular-nums` to every large PKR/sqft figure. Added a new `rates_sourced_date` field (backed by one constant, `RATES_SOURCED_DATE` in `data.py`, that also drives the disclaimer text so they can't drift apart) and a `SourcedBadge` component that surfaces it directly under the total cost on both estimate results and the rates page — turning the pricing fix into a visible trust signal instead of leaving it buried in small disclaimer text. This is a first pass, not a full redesign — no motion/illustration work done yet.

- [x] **Phase 0 — Foundation.** Repo structure, Next.js + FastAPI scaffolds, design tokens, base layout, CI-less local tooling (lint/build) verified.
- [x] **Phase 1 — Design System & Landing Page.** Reusable UI components (shadcn-based), dark/light theme, and a real landing page matching the product positioning.
- [x] **Phase 2 — Estimation Engine + API.** Quantity-takeoff logic (`POST /api/v1/estimate`) and material rates (`GET /api/v1/rates`), backed by placeholder-but-isolated data (see `backend/app/domain/estimation/data.py`) pending real bylaw/ratio/rate verification. No persistent DB yet — seed data in code; real storage lands once the Daily Material Rates admin UI (Phase 4) needs it.
- [x] **Phase 3 — Instant Estimate Flow.** Real `/estimate` page: form → `POST /api/v1/estimate` → itemized breakdown with category bars and an expandable per-material accordion. Frontend types are generated from the backend's live OpenAPI schema (`npm run types:api`) via openapi-typescript/openapi-fetch, so the API contract can't silently drift between the two.
- [x] **Phase 4 — Daily Material Rates Page.** Public `/rates` page: city-switchable table with a 14-day trend badge and sparkline per material. Backend now generates deterministic (seeded, not random-per-request) fabricated history ending at today's real rate, since there's no persistence yet to source real history from — see the `RATE_HISTORY_*` comment in `data.py`. **Admin entry interface is deferred to pair with Phase 6** (accounts/auth): an unauthenticated admin write endpoint would be a real security hole, not a shortcut worth taking.
- [x] **Phase 5 — Renovation Estimator.** Real `/renovation` page: room dimensions (length/width/height) + work-item checkboxes (floor tiling, wall tiling, painting, plastering) → `POST /api/v1/renovation` → the same category-bars/accordion breakdown UI as the main estimate, reused via a new shared `components/breakdown/` module rather than duplicated. Plastering reuses the exact cement/sand rates from the main engine; tiling introduces two newly-tracked materials (tiles, tile adhesive) that now also show up on the Phase 4 rates page automatically, for free.
- [x] **Phase 6 — Accounts, Auth, Saved Estimates, PDF Report Export.** First phase touching real persistence: PostgreSQL + SQLAlchemy (async) + Alembic migrations, replacing the placeholder-data-only backend. JWT bearer auth (`/auth/register`, `/login`, `/me`) — token-based per the architecture decision from Phase 0, not session cookies, so the future mobile app authenticates the same way. Saved estimates (`/saved-estimates`) store a snapshot of the request+response a user saw, not just inputs to recompute, so a saved estimate doesn't silently change if seed rates change later; ownership is enforced server-side (cross-user access returns 404, not 403, to avoid confirming another user's resource exists). Branded PDF export (reportlab) works both ad-hoc (no auth needed, matches "no signup required" positioning) and for saved estimates. Admin rate-entry deferred in Phase 4 still isn't built — auth existing now makes it possible, but it's not yet done.
- [x] **Phase 7 — Site Diary.** Moved ahead of the assistant and lead-flow phases (2026-09-25): confirmed via competitor research to be genuine whitespace (Tameer.ai has a marketplace + narrow calculator, nothing addressing "I'm overseas and can't see my site") — this is the intended core differentiator, not a generic feature. Scope decision: v1 is the project owner logging their own dated photo+note updates against a saved estimate ("project"), at `/account/[id]`; it does **not** yet build a contractor-invite/permission system for a separate contractor account to post into someone else's project — `author_id` is stored explicitly on each entry specifically so that's an additive change later, not a schema rework. The auto-budget-cross-check and payment-milestone ideas discussed earlier also stay out of v1. Photos are stored as bytes in Postgres (no cloud storage set up yet) and served through an auth-protected endpoint — `<img src>` can't carry a bearer token, so the frontend fetches the photo with `fetch()` + the token and renders it from a blob URL, the same pattern already used for PDF downloads. Verified end-to-end with a real image upload through the browser (not just a mocked file input): 5MB size cap and JPEG/PNG/WebP-only both enforced server-side, cross-user access to another owner's diary (list, photo, delete) all return 404, and the photo round-trips correctly (confirmed via non-zero `naturalWidth` after fetch, not just "an img tag exists").
**Room-by-room formula estimate (2026-09-25).** A second way to compute a house estimate, alongside the existing plot-size flow: `POST /api/v1/room-estimate` takes an actual room list ("4 bedrooms, 12×12ft; 1 kitchen, 10×12ft; ...") and computes exact floor area (sum of L×W) and exact wall area (sum of perimeters × ceiling height, less a door/window deduction) directly from that geometry, instead of approximating built-up area from plot size × bylaw coverage. Materials are matched to the correct surface — masonry and paint scale with the now-exact wall area, structural materials (cement/steel/aggregate) with floor area — via a small refactor to the shared pricing function (`priced_categories`, made to accept both areas instead of one) that is fully behavior-preserving for the existing plot-size estimate: it passes the same value for both parameters, verified by re-running the standing 10 Marla reference scenario and confirming byte-identical output before and after. Material rates and per-sqft ratios are the same already-sourced figures from the pricing recalibration pass, not new invented numbers — the accuracy gain here is exact geometry and correct area-to-material matching, not new formulas. Exposed in the UI as a "By Rooms" tab alongside "By Plot Size" on `/estimate`, sharing the same result components (category bars, accordion, PDF/save actions, sourced badge) as every other estimate type. City coverage unchanged (Islamabad/Rawalpindi only) — expanding to more of Punjab is a separate, unstarted scope decision.

**Room estimator: wet/dry rooms + counted doors/windows (2026-09-25).** Response to feedback that room-by-room shouldn't stop at plain geometry — a real 30-year builder prices a kitchen or bathroom differently from a bedroom of the same size, and prices doors/windows by the opening, not a flat wall-percentage guess. Each room group now carries a `room_type` (bedroom, kitchen, bathroom, lounge, dining, store, garage, other) and explicit `doors`/`windows` counts instead of a free-text label. Kitchens and bathrooms are flagged "wet areas" and get elevated per-sqft multipliers for electrical/plumbing (2.5x) and tiling/finishing (1.8x) — reflecting denser fixtures and full waterproofing/tiling versus a dry room's paint-and-a-switch — and their walls are excluded from the paint-quantity calculation (wet walls are tiled, not painted). Door/window counts replace the flat wall-opening-percentage deduction for this engine: each opening is subtracted by its real area (a standard door ~21 sqft, a window ~15 sqft, floored so net wall area never drops below 30% of gross) rather than an assumed percentage, and the woodwork/doors cost category is now priced directly per counted door and window (by quality grade) instead of a flat per-sqft benchmark — the estimate breakdown shows this as literal "9 doors x rate" / "14 windows x rate" line items, a genuine transparency upgrade over the old benchmark. This diverged enough from the shared plot-size pricing function that it's now its own bespoke pricing routine in `room_estimate_engine.py` rather than a further parameterization of `priced_categories` — a deliberate call not to force one function to do two increasingly different jobs. The wet/dry multipliers and per-opening costs are explicitly marked in `data.py` as industry-rule-of-thumb placeholders (the same "unverified but isolated" status as the rest of the pricing data), not a new researched source — the real claim is that these cost *categories* exist and matter, not that these exact multiplier values are precise. Verified end-to-end: direct engine test with a realistic mixed house (4 bedrooms, kitchen, 2 bathrooms, lounge), a live API call, and a rewritten 13-check Playwright suite covering the new room-type dropdown, wet/dry area display, and door/window counts on both desktop and mobile — plus the full 19-check regression sweep, all passing, zero console errors. Deliberately still out of scope: foundation as its own line item, boundary wall, water tank/septic tank, and a structure-type (RCC frame vs. load-bearing) toggle — none of these were requested, and each would need its own research pass before adding invented numbers for them.
